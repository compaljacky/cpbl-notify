# 模擬測試結論：公司團隊同步工作端 v1.0 設計弱點與優點

> 透過「Synapse HR Analytics 重建 design token」情境深度模擬 5 個 Phase（T1 → T6），曝露的設計優缺點與後續迭代方向。

---

## ✅ 設計成功：原始假設被驗證

### 1. Role agent 並行 vs lens 切換 — anchor bias 真的被避免

**情境**：T2 round-table 中 7 個 agent 並行提案，Facilitator Alex 等所有輸出後才開始收斂。

**驗證**：
- pm 與 sre 對「dark mode 上線時程」立場相反（pm depends、sre oppose）
- 若是順序執行，先說的 pm 「depends + 5 days buffer」可能讓後說的 sre 不敢直接 oppose
- **並行讓 sre 的 5 個 BLOCKS 完整成形，沒被先前的「general support」溫和化**

**結論**：✅ 機制如預期運作。記入 [[單人工作室AI協作系統]] 進階用法的回流候選（單人也可同時呼叫多 lens 並行）。

### 2. 三條紅線觸發機制全部生效

| 紅線 | 觸發點 | 生效情況 |
|---|---|---|
| 重大決策必走同步軌 | Emma 想直接修 ARCHITECTURE.md | sync-guard.js 攔截 → 走 design-review |
| Design Review 不能跳過 | DR-007 v1 sre BLOCKS | Emma 必須 v2 才能合併，沒有「之後再說」的空間 |
| 容量同步可視 | Fang 90% 🟡 | round-table 中 people-ops 主動標記，Alex 把 Fang 移出本 sprint，sprint 結束降到 75% 🟢 |

### 3. 雙軌不互鎖 — 個人軌可主動回流

**情境**：David 在 FOCUS-010 中發現 <AuditEntry> 硬編碼，透過 `/sync-context` 回流。

**驗證**：
- 不需要 round-table（影響太小）也能寫入 sync-context
- Facilitator 下次 SessionStart 自動看到
- 5 分鐘 emoji 投票決定 + 寫 decision-log

### 4. medium mode 9 個 agent 編排合理

**情境**：T2 派發 pm + product + tech-lead + design-lead + sre + qa + people-ops（7 個）。
**驗證**：
- engineer/designer 沒被派（已被 lead 取代）— 正確
- qa 自動加入 design-review — 正確
- people-ops 在 round-table 主動關照容量 — 正確

### 5. medium mode 的「組內共識」欄位有實質價值

**情境**：tech-lead 提案中明列 Chen / David / Alex 三人 stance（support / 中性 / support）。

**驗證**：
- David「中性」隱含的「不直接受影響」資訊被保留
- 若 tech-lead 直接代表全組統一意見，會錯過「sprint 中段大重構通常壞事」的個別觀察（David 在組內 poll 中提到的）

## 🟡 設計弱點：模擬曝露的問題

### 1. Lightweight sync 沒有正式 skill ⚠️ 高優先

**問題**：David 的 `/sync-context` 注入後，5/13 由 Chen + Emma 用 emoji 投票決定，這個機制在 CLAUDE.md 中沒有定義。

**目前發生情況**：靠 Facilitator ad-hoc 在 Slack 處理。

**風險**：
- 不同 Facilitator 處理方式不一致
- 沒留下可追溯的「為何這個沒走 round-table」的判準
- decision-log 條目會缺「來源 sync 類型」

**建議**：v1.1 新增 `/lightweight-sync` skill，定義：
- 何時用（影響 < 1 人天、單一檔案、不動禁改清單）
- 流程（Facilitator 開、相關 stakeholder emoji 投票、寫 decision-log）
- 與正式 round-table 的明確界線

### 2. STATE.json 缺 `sync_queue.scope` 欄位 ⚠️ 中優先

**問題**：sync_queue 中的條目應該標明「lightweight / heavyweight」，但 schema 沒有此欄位。

**目前發生情況**：模擬中 ad-hoc 加上 `"scope": "lightweight"`。

**建議**：v1.1 schema 升 1.1，新增 `sync_queue[].scope` 欄位，同時 capacity-guard.js 可判斷是否該觸發 round-table。

### 3. design-review BLOCKS 處理過程缺「mini-sync」機制 ⚠️ 高優先

**問題**：DR-007 v1 有 5 個 BLOCKS，Emma 一個人花 14 小時獨自修。事後 retro 中 Emma 自己說「應該開臨時 mini-sync 一起想」。

**目前發生情況**：BLOCKS 後流程是「提案者修 → /design-review 重跑」，沒有中間的協作步驟。

**風險**：
- 提案者孤立感
- 修正速度慢（14 小時 vs 集思 2 小時）
- 提案者可能誤解 BLOCKS 意圖（畢竟是 sre agent 的文字）

**建議**：v1.1 在 `/design-review` skill 加入「BLOCKS ≥ 3 → 自動觸發 30 分鐘 mini-sync」邏輯。或新增 `/design-review-rescue [DR-XXX]` 主動觸發。

### 4. codemod 與類似自動化工具缺「confidence」維度 ⚠️ 中優先

**問題**：FOCUS-012 中 codemod 對 inline hex 一律警告，但實際上有些是 100% 安全（test fixture 中的色值）、有些需 review（storybook 範例）。

**這不是範本層次的問題，是工程實踐**，但反映本範本對「個人軌的工具品質」沒有 PRINCIPLES。

**建議**：v1.1 在 PRINCIPLES.md 加 default 原則「自動化工具須提供 confidence score（auto/review-needed）」。

### 5. People-ops agent 的「保密」與「透明」之間沒有明確界線 ⚠️ 低優先

**問題**：people-ops 在 round-table 中主動標記 Fang 容量🟡，這雖然有用但有「公開個人狀態」的疑慮。

**目前發生情況**：模擬中 Fang 自己後來說「我才知道團隊有看到」，是正面感受。但若有人本來不希望被標記呢？

**建議**：v1.1 在 people-ops agent definition 加「揭露原則」：
- 容量數字 → 公開（影響團隊決策）
- 容量原因（家庭、健康）→ 不公開（人格界線）
- 心理狀態評估 → 不公開（除非當事人同意）

### 6. medium mode 下「engineer/designer 個人軌 lens」與「同步軌 tech-lead/design-lead 」的角色定位混淆 ⚠️ 中優先

**問題**：Chen 在個人軌可以 `/lens engineer`，但同步軌是 tech-lead 出場。Chen 自己在個人軌切換時，是在跟 tech-lead 對話還是 engineer 對話？

**目前發生情況**：模擬中沒明顯出現問題，但 Chen 若在個人軌想質疑 tech-lead 在 round-table 的判斷，他要怎麼做？

**建議**：v1.1 釐清個人軌 lens 的可用對象：
- engineer/designer（個人專業視角）— 個人軌可用
- tech-lead/design-lead（協調代表視角）— 個人軌**不可用**（因為 lead 是同步軌身分）

### 7. raw/ 文件編譯到 round-table 草稿的流程沒寫進 `/read-raw` skill ⚠️ 低優先

**問題**：模擬中 Alex 用 `/read-raw` 把 Emma 的提案 raw 文件編譯為「round-table 草稿」，但 `/read-raw` skill 描述沒明確列「→ round-tables/_drafts/」這條分流路徑。

**建議**：v1.1 補完 `/read-raw` 的分流規則。

## 🎯 對「公司團隊同步工作端」整體判斷

### 適合採用的訊號
- 團隊已厭倦「PM 寫完 spec 才丟工程師」的階段交付
- 有專屬 Facilitator（Tech Lead 或 PM）能花時間主持同步軌
- 團隊對「文件留下決策歷史」有共識

### 不適合採用的訊號
- 團隊文化是「快速 ship、文件之後再補」
- 沒有 Facilitator 角色
- 成員對 sync session 有抗拒（覺得「又是會議」）

### 與既有角色端搭配
- 公司團隊同步工作端 = **Facilitator 用的**
- 一般成員仍可在自己的工程目錄用 [[工程師端AI協作系統]] / [[HTML設計師端AI協作系統]] 等
- 重要決策時到 Facilitator 那邊參與 round-table / design-review

## 結論

公司團隊同步工作端 v1.0 的核心設計（Role agent 並行、三種同步儀式、雙軌設計、團隊容量看板）在模擬中成功運作。曝露的弱點集中在「協作邊緣案例」（lightweight sync、BLOCKS 處理協作、個人 lens 與 lead 角色界線），這些都是可在 v1.1 補上的「擴充」而非「重構」。

**建議下一步**：
1. 真實團隊試跑 1–2 個 sprint，蒐集實戰反饋
2. 依本次模擬建議啟動 v1.1 規劃（走 Phase 5 範本迭代）
3. 此模擬本身可作為 onboarding 教材，幫新團隊理解「同步軌 vs 個人軌」與「Role agent 並行」的設計思維
