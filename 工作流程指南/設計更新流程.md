# 設計更新流程：HTML設計師端 ⇄ 公司團隊同步工作端

> 目標讀者：團隊中的設計師（不論個人軌主用 [[HTML設計師端AI協作系統]]，還是同步軌參與本範本）。
> 解答的問題：「我想改設計，要做哪些動作？」

---

## 🗺️ 兩個系統的職責分工

設計師同時用兩個 Claude 環境：

| 系統 | 你在哪裡用 | 處理什麼 |
|---|---|---|
| **HTML設計師端 v3**（個人軌） | 你自己的 Claude session | 個人創作：畫稿、HTML 原型、token 設計、Persona/Journey、設計研究 |
| **公司團隊同步工作端 v2.0**（同步軌） | Facilitator 的 Claude session（你到那邊參與） | 跨職能討論、評審、發版、共識決策 |

兩者透過 **git** 同步 — 你在 HTML設計師端 commit 的設計檔案，Facilitator 拉下來時就能在同步軌中引用。

---

## 🎯 決策樹：你的改動屬於哪個 Scope？

四種 scope，每種走不同流程。誤判 scope 是最常見的踩坑點。

### Scope A — 小調整（個人軌即可）

**判定條件（必須全滿足）**：
- ✅ 改動 ≤ 1 個元件 / 1 個畫面
- ✅ 不動 design token
- ✅ 不影響 a11y 對比度 / 鍵盤導航
- ✅ 不影響其他職能（工程、測試、SRE）
- ✅ < 1 人天工作量

**典型範例**：
- 改 button label 文字
- 調 modal 的 close icon 位置
- 修一個 tooltip 措辭
- 換一張 onboarding 插圖

**流程**：
```
1. 在 HTML設計師端 開 Claude，做設計
2. 直接 commit、開 PR
3. 走標準 PR review（同事檢查）
4. merge
```

**不需要**：
- ❌ round-table
- ❌ design-review
- ❌ sync-context

---

### Scope B — 中型改動（lightweight-sync 或 round-table）

**判定條件（任一即觸發）**：
- ✅ 動到 design token（顏色、間距、字級）
- ✅ 影響多個元件（≥ 3）
- ✅ 影響 a11y（對比度變化、新互動模式）
- ✅ 跨 ≥ 2 職能（如改 form 元件影響 e2e 測試 → qa）

**典型範例**：
- 修 brand color 主色
- 加新的 spacing token
- 改 form 元件 error 狀態
- 重做 navigation 結構

**流程（依影響職能數）**：

#### B-1：只影響 designer + frontend engineer（≤ 3 人決定）→ `/lightweight-sync`
```
1. HTML設計師端 完成設計草稿（含 token diff）
2. 到 Facilitator 那邊：/lightweight-sync 修 brand color 主色
3. Slack/Teams 5 分鐘 emoji 投票（你 + frontend engineer + Facilitator）
4. 全員 🟦 → 寫 decision-log，回個人軌實作
5. /individual-focus 完成實作
6. 開 PR、走標準 review、merge
```

#### B-2：影響 ≥ 2 職能 → `/round-table` + `/design-review`
```
1. HTML設計師端 完成設計草稿
2. 到 Facilitator 那邊：/round-table 修 form error 狀態
   → 派發 6 個 role agents 並行提案
   → 收斂後決定走 design-review
3. /design-review DR-XXX
   → 受影響角色（engineer, qa, ...）並行 verdict
   → 全 APPROVED 才能實作
4. 回個人軌：/individual-focus
5. 實作 → critic → PR → merge
```

---

### Scope C — 大型重構（必走 round-table + 多輪 design-review + 可能 mob）

**判定條件（任一即觸發）**：
- ✅ 改 design token 系統結構（如 v1.0 模擬中的 dual-tier 重建）
- ✅ 引入新 atomic design 層級
- ✅ 全面改 grid system
- ✅ 換主題引擎（如加 dark mode 並改 token 結構）
- ✅ 修改 ARCHITECTURE.md「設計系統」章節（**禁改清單**）

**典型範例**：
- 重建 design token 系統（v1.0 模擬 DR-007）
- 引入 Tailwind v4 並廢棄舊 CSS
- 從 component-based 改為 atomic-based

**流程**：
```
1. HTML設計師端 做 prototype（≤ 4 小時）
   → 不寫死 production code，只驗證可行性
2. 到 Facilitator 那邊：/round-table 重建 design token 系統
   → 9 個 role agents（medium mode）並行提案
   → 預期會出現 sre BLOCKS、pm 容量警告等
   → 收斂後決定 split 策略（foundation 先行、漸進遷移）
3. /design-review DR-XXX（很可能 v1 BLOCKS → v2）
   → 若 BLOCKS ≥ 3，自動建議 mini-sync rescue
4. design-review 通過後：
   - foundation 階段 → /mob 群體開發（你 + tech-lead + frontend engineer）
   - 元件遷移階段 → 個人軌 /individual-focus 分批
5. canary 部署：staging 3 天 → 內部 dogfood 1 天 → prod 對齊維護窗
6. /team-retro 回顧
```

詳細範例見 `示範運行/`（v1.0 模擬完整 trace）。

---

### Scope D — 跨團隊設計（外部協作，不在本範本範圍）

**判定條件**：
- ✅ 你的 design system 被另一個團隊使用
- ✅ 改動會影響另一個團隊的產品

**流程（建議）**：
```
1. 本團隊先走 Scope C 流程，內部達成共識
2. Facilitator 與外部團隊 PM 對接（人對人，不在本範本內）
3. 雙方協議影響範圍、過渡期、breaking change 通知
4. 本團隊執行階段中，向外部團隊 sync release notes
```

本範本不處理跨團隊協作。如果跨團隊協作頻繁，考慮加入**跨專案層級**工具（如 PMO 端，雖然本範本未採納，但可在公司層級另設）。

## 🎨 designer 與 design-lead agent 的差別

| Mode | 同步軌出場的 agent | 個人軌可切換 lens | 理由 |
|---|---|---|---|
| **small** (3–6 人) | `designer` | `/lens designer` ✅ | 一人一視角 |
| **medium** (7–15 人) | `design-lead` | `/lens designer` ✅ / `/lens design-lead` ❌ | design-lead 是組內共識代表，個人軌無法 poll 組內 |

medium mode 實務：
- 你（個別設計師）在個人軌用 HTML設計師端
- 同步軌出場的是 design-lead（如果你就是 lead，那就是你；如果不是，是另一位）
- design-lead 在 round-table 提案前會 poll 組內：「Alice 在 frontend、Bob 在 visual，他們對這個議題的立場是什麼？」

## ⚠️ 設計師最容易踩的 3 個坑

### 坑 1：在個人軌靜默改 design token
**症狀**：你直接在 HTML設計師端 改了 `tokens/semantic.css`，commit 之後同步軌還不知道。
**Hook 會擋**：`sync-guard.js` 偵測到你在個人軌（active_sync_session 為 null）改禁改清單檔案 → 阻擋 commit。
**正確做法**：先到 Facilitator 那邊走 `/design-review`，APPROVED 後再改。

### 坑 2：不確定 scope 就直接走最重的流程
**症狀**：明明只是改個 button label，卻開了 round-table 等 6 個 agent 並行提案，浪費時間。
**正確做法**：先用上面決策樹判斷 scope。Scope A（小調整）就直接 PR，不要走同步軌。

### 坑 3：design-review BLOCKS 之後一個人扛
**症狀**：DR-XXX v1 收到 5 個 BLOCKS（sre + qa + pm + ...），你想自己默默修，14 小時還沒交 v2。
**v1.1 起的機制**：BLOCKS ≥ 3 自動建議 mini-sync rescue（30 分鐘 stakeholder 集思）。**接受這個建議**。
**正確做法**：30 分鐘集思通常比 14 小時獨自修更快、品質更高。

## ❓ FAQ

**Q：我是 small mode 團隊唯一的設計師，要走這個流程嗎？**
A：要，但會比較簡化。你個人軌在 HTML設計師端 做大部分工作，重大改動到 Facilitator 那邊走 `/round-table`。在 round-table 中你「同時是設計師」與「同步軌中代表設計視角的真人」，不衝突。

**Q：HTML設計師端 與 公司團隊同步工作端 的設計檔案放哪？**
A：同一個 git repo。HTML設計師端 的 `src/` 與本範本的 `knowledge/design-system/` 是同一份，只是不同 Claude 環境讀同一份檔案。

**Q：mob session 的 driver 一定要是設計師嗎？**
A：看任務性質。如果是動 token CSS → 設計師 + frontend engineer 輪流；如果是動 ARCHITECTURE.md → tech-lead 主導。

**Q：我提的設計被 round-table 否決了，怎麼辦？**
A：兩條路徑：
- 否決理由可解 → 修正後再開 round-table
- 否決理由不可解 → 寫進 `knowledge/explorations/{構思}/04_pivot紀錄.md` 作為決策歷程，之後想到新方向再回來

**Q：我想改 design token 但其他設計師也在改 token，怎麼辦？**
A：在同步軌的 `context/individual-tracks.md` 看其他設計師的 active focus。如果衝突 → 先在 `/lightweight-sync` 對齊次序。
