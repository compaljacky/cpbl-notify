# 每週上版流程：AI 自動化下的時間驅動 release

> 解答的問題：「個人成員大量用 AI 產出，每週要上版一次，整個週節奏怎麼跑？品質閘門怎麼保證？」

---

## 🎯 核心轉變

| 維度 | 舊（事件驅動） | 新（時間驅動 + AI 自動化） |
|---|---|---|
| **release 時機** | 「準備好了就上」 | **每週至少一次**（必要時 mid-week patch） |
| **個人軌節奏** | focus block 1-2 週 | focus block 縮短為 1-3 天，週內可跑多個 |
| **產出比例** | 主要人工 | AI 產出大量初稿、人工 review 與決策 |
| **品質瓶頸** | 實作（寫程式慢） | **review / decision**（AI 解了實作瓶頸） |
| **critic 角色** | 完成前必跑 | **AI 生成內容必過 critic**（PRINCIPLES #7） |
| **同步議題承載** | 多場 round-table 可分散 | 必須收斂在週初，避免擠壓 release |
| **retro** | 版本驅動（每 release 一次） | **週週短版（30 min）+ 雙週長版（90 min）** |

## 🗓️ 週節奏（典型一週）

預設安排（時區：Asia/Taipei；其他時區依比例調整）：

```
週一 09:00–11:00   /weekly-sync             ← 上週回顧 + 本週規劃 + capacity flush
週一 11:00–12:00   /round-table（如有新議題）← 本週主議題對齊
週一 PM ~ 週三      個人 /individual-focus   ← AI 產出 + 人工 review，多 focus 並行
週二 ~ 週四        /design-review（成熟提案）← 受影響角色並行 verdict
週三 / 週四        /mob（關鍵實作）          ← 群體開發 foundation 等
週四 PM            個人 focus 收尾、跑 critic
週五 09:00–10:00   /integration             ← 全 role agent 同步檢查、全 GO 才繼續
週五 10:00–12:00   /weekly-release          ← canary → staging → prod
週五 14:00         監測 + 公告               ← 24h 觀察期啟動
週五 16:30–17:00   /team-retro mode=quick   ← 短版 retro（30 分鐘）
雙週週五 16:30–18:00  /team-retro mode=full  ← 長版 retro（90 分鐘，取代當週短版）
週末              oncall                    ← sre 主、其他人 backup
```

### 例外情境（不照預設節奏跑）

| 情境 | 變動 |
|---|---|
| 連假週 | 上版提前到週四，release 後再放假 |
| 客戶合約有特定維護窗 | 上版時間對齊維護窗（pm 在 weekly-sync 中 flag） |
| Hotfix 必要 | mid-week 走 `/weekly-release mode=patch`（簡化版，跳過 weekly-sync） |
| 上週 release 出 incident | 本週 release 暫緩 1 週，先做 incident-retro |

## 🤖 AI 自動化下的個人軌

### 個人成員的典型一日

```
09:00-09:30  /individual-focus 開卡（含 AI assist 預估）
09:30-12:00  AI 大量產出（程式 / 設計 / 文件初稿）
                ↓
                個人成員 review + iteration
12:00-13:00  休息
13:00-15:00  繼續 AI iteration，或切到下一個 focus
15:00-16:30  跑 critic subagent（強制）
                  ├── critic APPROVED → commit + PR
                  └── critic CHANGES_REQUIRED → 修正後再跑
16:30-17:00  /focus-end 或繼續到隔天
17:00         session_stop.py（記錄 total hours + ai_assist_hours）
```

### `/individual-focus` 開卡時的 AI 預估

v2.1 起，開 focus 時系統會問：
```
此 focus 預估：
- 總工時：X 小時
- 其中 AI 預估產出比例：__ %（如 60% 表示 AI 產出 60%、人工 40%）
- AI 產出類型：[code / docs / design / mixed]
```

PM agent 會用此資訊評估 capacity 與品質風險：
- AI 比例 > 70% → critic 必跑「強化版」（v2.1 critic 對 AI 產出的提示加深）
- AI 比例 > 90% + 跨核心模組 → 強烈建議改走 mob session（不能單人扛 AI 產出進核心）

## 🔒 品質閘門（PRINCIPLES #7：AI 生成必過 critic）

### 規則

任何「AI 生成的內容」在 commit 前都必須跑 critic subagent。
- 「AI 生成」= Claude / Cursor / Copilot 等 AI 產出，包含部分人工修改的也算
- 「commit 前」= 在 `git add` → `git commit` 之間
- 「critic」= 本範本的 critic subagent，不是 AI 自我檢查、不是 linter

### 違反 = 違反紅線二（Design Review 不能跳過的延伸）

`/individual-focus`、`/implement` 流程中 critic 已是強制步驟，本原則只是補強「AI 自動化下不能因為產出快就略過 critic」。

### Critic 對 AI 產出的審查重點（v2.1 強化）

當 critic 偵測到本次變動的 commit message 含 `[ai-assisted]` 標記或 git note 標明 AI 產出，會：
- 加查「AI 容易出錯類型」：null/undefined 處理、邊界 case、N+1 query、unbounded loop
- 加查「AI 容易過度設計類型」：不必要的 abstraction、不必要的 interface
- 加查「AI 容易遺漏類型」：error handling、a11y、i18n
- 對 PR 的描述內文做語意檢查（AI 寫的 PR 描述常虛胖）

### 例外（不需走 critic）

- 純文件 typo 修正（< 5 字）
- gitignore / package.json 等 metadata 改動
- AI 只是 reformat（沒改邏輯）

例外要在 commit message 註明 `[no-critic: typo/metadata/format]`，由 hook 抽查記錄。

## 📊 capacity-board v2.1：AI hours 欄位

### 新格式

```
| 成員 | 角色 | 本週上限 | 已用 | AI assist | % | 燈號 | 當前 focus |
|---|---|---|---|---|---|---|---|
| Alice | engineer | 35 | 28 | 18 | 80 | 🟡 | FOCUS-007 |
| Bob | designer | 30 | 22 | 8 | 73 | 🟢 | FOCUS-005 |
| Carol | pm | 35 | 30 | 4 | 86 | 🟡 | （無 focus）|

整體：80/100h（80% 🟡）
AI assist 整體：30h（佔總工時 38%）
```

### 解讀

- **已用 hours**：人坐在電腦前的真實時數（含 AI iteration、review、思考）
- **AI assist hours**：其中由 AI 主導產出的時段（人主要在 review/iteration）
- **比例**：AI assist / 已用，PM 看此判斷「effective output」

### PM 如何用此資料

| 情境 | PM 判斷 |
|---|---|
| AI 比例 > 60%、容量 🟡 | effective output 高，本週承載合理 |
| AI 比例 < 30%、容量 🟡 | 真的人手吃緊，建議重排或砍 scope |
| AI 比例 > 80%、critic CHANGES_REQUIRED 比例高 | 警告：AI 產出品質下降，可能要降速 |
| AI 比例 = 100%、單人扛核心改動 | BLOCKS：必須改走 mob session |

### session_stop.py v2.1 詢問格式

```
本次 session 是誰執行？: Alice
軌道類型（sync / individual）: individual
本次 session 工時（小時）: 4.5
其中 AI 主導產出的時段約多少小時？: 3.0
本次 critic 結果：(approved / changes-required / not-run): approved
```

## 🔄 `/weekly-release` skill 主流程

### 觸發
- 週五早（預設、planned weekly）
- mid-week patch（hotfix）

### 步驟（planned weekly）

```
1. 確認在 main 分支、所有 feature/* 該 merge 的都 merge 了
2. 跑 /integration（全 role agent 同步檢查）
   - 全 GO → 繼續
   - 有 NO-GO → 回頭修，整合延後
3. 自動產生 release notes 草稿（含本週 closed FOCUS / DR 列表）
4. /release-cut 由 sre 主導環境推進（dev → staging → prod）
5. 監測 24 小時
6. 觸發 /team-retro mode=quick（30 分鐘）
7. 寫 knowledge/releases/vX.Y.Z.md
```

### 步驟（mid-week patch）

```
1. /weekly-release mode=patch
2. 跳過 /integration（patch 範圍小，由 sre + 主修者直接判斷）
3. /release-cut --canary（更謹慎的 canary）
4. 寫 release notes 補在原本週 release 的「mid-week patches」段
5. 不觸發 /team-retro（等本週五的 quick retro 一起回顧）
```

## 📋 雙模式 retro

### Quick retro（每週五 30 分鐘）

```
=== Sprint vX.Y.Z Quick Retro @ YYYY-MM-DD ===
日期：YYYY-MM-DD
參與：全員 (≤ 8 人 stand-up 形式)

📦 本週交付（一句話總結）：

⚡ 容量：
  - 本週整體 X% / 燈號
  - AI assist 平均 Y%

🚦 三個快速問答（每人 30 秒，輪一圈）：
  1. 本週最有效率的事？
  2. 本週最卡的事？
  3. 下週要試的事？

💡 即時 Lessons（≤ 2 條）：
  - 

⏭️ 下週主題（一句話）：
```

存入 `knowledge/retros/sprint-retros/YYYY-MM-DD_quick.md`。

### Full retro（每雙週 90 分鐘）

完整版本，含 Continue/Stop/Try、Lessons 深度討論、團隊健康自評（PM 主導容量段）等。

排程規則：
- 雙週的偶數週週五 → full（取代 quick）
- 雙週的奇數週週五 → quick

或更彈性：
- 任何成員主動提出「議題太多，本週要 full」 → 走 full
- 連續 4 週 quick → 強制下週 full（避免持續累積未討論議題）

## ⚠️ AI 自動化下的 5 個常見坑

### 坑 1：AI 產出量大，critic 跟不上
**症狀**：個人軌成員一天產出 5 個 PR，critic 排隊處理不完，某些直接 merge。
**正解**：
- 個人成員自己跑 critic（個人軌的 critic 是 in-session，不需要排隊）
- 不是「Facilitator 跑 critic」是「PR 作者跑 critic」
- 違規 = 違反 PRINCIPLES #7

### 坑 2：每週上版壓力導致同步議題被擠壓
**症狀**：週四發現有架構議題該開 round-table，但週五要上版，乾脆「下週再說」。
**正解**：
- 議題進 sync_queue 而非略過
- 若議題 block 本週 release → 立刻開 round-table，必要時延 release（PM 紅線一）
- 不該為「上版時程」犧牲「重大決策必走同步軌」

### 坑 3：AI 產出的 PR 描述虛胖、看似完整實則不準
**症狀**：AI 寫 PR 描述「Implements user authentication with proper error handling」，實際只覆蓋 happy path。
**正解**：
- critic v2.1 加 PR 描述語意檢查
- 真人 reviewer 必須對 PR 描述至少抽查一段
- Lessons：發現一次 → 加 PRINCIPLES Lessons Learned，下次強化

### 坑 4：AI 比例 100% 的 focus 直接進核心模組
**症狀**：成員整個 focus 全部 AI 產出 + 人工 review，但任務碰核心架構。
**正解**：
- v2.1 規則：AI 比例 > 90% + 跨核心模組 → 強烈建議改走 mob
- mob 中真人 driver/navigator 配對能抓 AI 看不到的隱性脈絡
- 個人成員若堅持單人扛，design-review 中 BLOCKS 風險高

### 坑 5：每週 retro 變成例行儀式、失去學習意義
**症狀**：quick retro 每週同樣三條「AI 太強」「critic 卡」「下週多用 mob」，無新洞察。
**正解**：
- 強制每 4 週走 full retro（深度討論）
- full retro 時把過去 4 週的 quick retro 條目整合，找重複模式
- 重複 ≥ 3 次的議題自動觸發 round-table 討論結構性解法

## 🔗 觸發判斷速查

| 你想做的事 | 動作 |
|---|---|
| 我有個 AI 產出的 PR 要交 | 跑 critic（強制）→ commit message 加 `[ai-assisted]` → push |
| 我發現 AI 產出常出某種 bug | `/sync-context` 注入觸發 round-table 討論 critic 規則調整 |
| 本週要上版了但我 focus 還沒完 | 看是否能 split：把已穩定段落 merge 上版、剩下下週繼續 |
| 我覺得 weekly-release 太緊張 | full retro 中提出，全團隊討論調整節奏 |
| 我想跳過本週 retro | 不行（至少 quick）；除非全員另外時段補 |
| Hotfix 要 mid-week 上 | `/weekly-release mode=patch` |

## ❓ FAQ

**Q：為什麼是「每週至少一次」而不是「每週剛好一次」？**
A：避免「累一週的 hotfix 等到週五一起上」的反模式。Hotfix 該即時 mid-week patch；planned 大版本走週五。

**Q：sprint 概念還適用嗎？**
A：適用但弱化。本範本中「週」就是 sprint，sprint planning = weekly-sync、sprint review = quick/full retro。Backlog 仍存在但比傳統 scrum 更輕量。

**Q：AI 比例怎麼估？**
A：粗估即可，不需精確。session_stop 詢問時憑感覺：
- 0–20%：AI 偶爾用（如查文件、寫 commit message）
- 20–50%：AI 寫初稿、人工大幅改寫
- 50–80%：AI 寫主體、人工調 + 補
- 80–100%：AI 寫絕大部分、人工只 review + 微調

**Q：如果 critic 一直 CHANGES_REQUIRED 我修不完怎辦？**
A：兩種可能 — (1) AI 產出品質低於團隊標準 → 限制 AI 用法；(2) 你的 spec 模糊 → critic 抓得太嚴 → 補 design-review AC。

**Q：每週上版壓力會不會降低設計品質？**
A：會 — 如果你把「上版」誤解為「全部功能完成」。週上版的精神是「累積的小進展定期釋出」，不是「每週塞滿大功能」。Roadmap 的 Now/Next/Later 結構有助於拆小。

**Q：AI 寫的 round-table 提案 / design-review verdict 算嗎？**
A：role agent 本來就是 AI（Claude）。關鍵是「人類成員的最終決策」要明確記錄。round-table 收斂、Verdict 接受/否決都由真人 Facilitator 拍板。

**Q：我們團隊還沒導 AI 自動化，這份指南適用嗎？**
A：部分適用：
- 週節奏 / 雙模式 retro / `/weekly-release` skill：直接適用
- AI 比例追蹤、PRINCIPLES #7：等到開始導 AI 時再加（先把欄位空著就行）
